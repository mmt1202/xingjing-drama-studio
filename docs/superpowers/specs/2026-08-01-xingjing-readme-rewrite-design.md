# 星镜剧创双语 README 改写设计

## 1. 背景

根目录 `README.md` 与 `README.en.md` 仍以 ArcReel 为项目主体，包含旧项目名称、仓库徽章、克隆地址、交流群、产品定位和功能说明。这与仓库当前的星镜剧创 v9.2 产品基线、代码模块和开发进度不一致。

本次改写将 README 的主体切换为星镜剧创，同时保留对现有代码来源和许可证义务的准确说明。

## 2. 目标读者

README 同时服务两类读者：

1. 产品、业务和潜在使用者：需要快速理解星镜剧创解决什么问题、覆盖哪些生产环节、适合哪些团队。
2. 开发者和评审者：需要找到系统边界、当前状态、代码结构、启动命令、质量门禁和权威文档入口。

中文与英文 README 面向相同读者，章节结构和事实口径保持一致。

## 3. 内容策略

采用“分层说明”结构：

1. 先介绍星镜剧创的产品定位、用户、四端范围和端到端工作流。
2. 再按业务领域概述内容理解、资产、分镜、模型生成、音频、剪辑、协作、计费、合规、生态等能力。
3. 单独说明 P0、P1、P2 路线以及当前仍处于开发和联合验收阶段，避免把规划能力表述成已经完成的功能。
4. 后半部分提供当前代码架构、技术栈、仓库目录、本地开发、质量检查、部署和文档索引。

README 不展开 197 个页面的逐项清单，而是链接到权威需求台账供深入查询。

## 4. 章节结构

中英文 README 使用以下对应结构：

1. 品牌标题、语言切换和一句话定位
2. 开发状态声明
3. 产品概述与目标用户
4. 端到端生产流程
5. 四个产品端
6. 核心能力
7. 交付阶段与当前状态
8. 系统架构
9. 技术栈
10. 仓库结构
11. 快速开始与本地开发
12. 测试和质量门禁
13. 文档导航
14. 贡献、许可证与上游署名

## 5. 事实来源

README 中的产品和工程描述按以下优先级取值：

1. `docs/product/v9.2/00-governance/source-of-truth.md`
2. `docs/product/v9.2/01-product/scope-and-priority.md`
3. `docs/product/v9.2/04-architecture/system-architecture.md`
4. `docs/project/requirements/01-需求总览与完成度.md`
5. `docs/project/XINGJING_REQUIREMENTS_PROJECT.md`
6. 仓库中的实际目录、配置、脚本和开发命令

对于规划架构和当前代码形态不一致的部分，README 会明确使用“目标架构”或“当前仓库”限定语，不混为一谈。

## 6. 品牌与上游边界

- 项目主体名称使用“星镜剧创”，英文名称使用“Xingjing Drama Studio”。
- 仓库入口使用 `https://github.com/mmt1202/xingjing`，不再使用 ArcReel 的克隆地址或状态徽章。
- 删除以 ArcReel 为主体的产品宣传、交流群和联系信息。
- `NOTICE` 要求修改版本保留 `Powered by ArcReel` 声明和原仓库链接，因此在许可证与致谢部分保留简短、明确的上游署名。
- 不使用 ArcReel 名称或标识充当星镜剧创品牌，不歪曲软件来源。

## 7. 状态表达规则

- 将完整 v9.2 范围称为“产品基线”“规划能力”或“交付范围”。
- 将已经存在但尚未通过星镜联合验收的能力称为“开发中”或“兼容基础”。
- 不使用“全部完成”“生产可用”“已上线”等无证据结论。
- README 只展示稳定的阶段概览；精确完成状态统一链接到需求台账。

## 8. 开发者入口

快速开始以当前仓库可执行的开发命令为准：

- Python 3.12+、Node.js 20.19+、`uv`、`pnpm` 和 FFmpeg 为基础依赖。
- 后端使用限定 `--reload-dir server --reload-dir lib` 的 uvicorn 命令。
- 前端使用 `pnpm dev`。
- 数据迁移使用 Alembic。
- Python、前端和 Java 平台模块分别列出对应的测试、lint、类型检查和构建命令。
- Docker 部署只链接现有部署文件，并标注环境配置要求，不承诺尚未验证的生产状态。

## 9. 验收标准

改写完成后必须满足：

1. `README.md` 和 `README.en.md` 结构一致，内部链接有效。
2. 两份 README 均以星镜剧创为主体，不残留 ArcReel 的品牌标题、旧仓库徽章、旧克隆命令、交流群或商业联系方式。
3. ArcReel 只在兼容基础说明和许可证要求的上游署名中出现。
4. 产品范围、页面数量、P0/P1/P2 数量、技术架构和开发命令与当前权威资料一致。
5. 规划能力与已验证能力明确区分。
6. Markdown 标题层级、表格、代码块、相对链接和 Mermaid 图语法完整。
7. 通过链接检查、关键字残留扫描和 `git diff --check`。

## 10. 非目标

- 不修改产品需求、架构规格、许可证或 `NOTICE`。
- 不在本次任务中重命名 Python 包、前端包、环境变量或代码中的 ArcReel 兼容标识。
- 不修改应用界面品牌、后端行为、部署配置或供应商实现。
- 不把 README 扩展成逐页 PRD、完整 API 参考或运维手册。
