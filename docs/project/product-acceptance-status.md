## 预算实现依据及保留边界

- 项目配置的旧 `budgetMinor` 明示 CNY，迁移为确认的 SQL 策略；单集文件值保留为计划，确认后以 SQL 策略为准。0 是合法零预算，不能与未设置上限混淆。
- 三类生产 hold 已在同一数据库；项目预算占用应按实际消费加 active hold 的剩余预留汇总，不能使用工作区账户的总消费或从导出依赖重复计入共享素材。
- M06 的 M05/M18 来源、M08 固定时间线能证明单集；M04 主体资产计入项目共有制作。普通生成和 M07 首次付费请求选择并固定归属，后续重试不能改变。旧未归属费用不能自动猜测剧集。
- 除三类初始冻结外，还须覆盖 M07/M08 原 hold 重新激活，以及预算下调和解除上限的权限与审计。等待锁后再次识别同键已完成请求，幂等回放为零新增占用。
- 共同项目锁、账户锁及任务/hold 锁顺序已复核并通过真实 PostgreSQL 跨模块并发验证；正式外部消费仍未联合验收。

## 实际供应商适配的接线约束

- 现有加密 `provider_credential` 已通过精确 ID 和工作区授权接入原生图片；只保存密钥仍不会自动启用 M06。部署方须配置模型、报价与明确授权，不能悄悄选择另一条 active 凭据。
- 原生图片执行器通过底层 `assemble_backend` 与 `ImageGenerationRequest` 执行文生图及参考编辑，固定 provider/model 和已验证输入，不引入旧流水线的重复写回和账本扣费。
- 执行必须持久化认领和确定未发送/提交未知/已完成状态，不能仅开内存后台 task。未知同步调用不能按 TTL 重新付费；本地 execution ID 不能冒充供应商 job ID。
- 产物走 M06 artifact store 和受信任完成事务；明确用户结算策略及版本，不能把供应商美元用量、预估费用或旧 Ledger 扣费重复记为用户实际消费。
- 视频可复用底层 `VideoBackend.generate/resume_video`，但供应商 job ID 持久化需注入 M06 专用回调；现有 mixin 写的是 legacy queue，不能直接传 M06 task ID。
