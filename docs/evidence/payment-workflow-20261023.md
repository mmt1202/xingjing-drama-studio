## 范围与原型

按用户确认的“先接统一支付网关，后续配置渠道”实现应用侧订单和退款流程。原型依据为 `D:/aivideo/xingjing_web_full_v9_2_nav_fix/creator/billing.html` 及后台订单页面；AD-034 原型为通用占位页，退款业务按真实状态和审批要求补齐。冻结的 `docs/product/v9.2` 未修改。

创作者页面沿用共享侧栏、顶栏和内容容器，还原四项指标、七日趋势/流水与右侧套餐/消耗分布/充值包结构。余额、冻结、实际结算、套餐和流水来自同一账务快照；UTC 日期、筛选作用范围、账面金额与可用余额变动分别说明。缺少预算、预测或套餐事实时显示未知，未建立账户不显示虚构零余额。

当前权威账本仍是货币最小单位，不是冻结规格中的 `credit_micros` 与完整 funding lots。充值包的应付和入账金额相同，由服务端配置；没有复制原型中未经批准的兑换报价。后台订单和退款页按当前可信租户/工作区读取同一数据，不代表已经完成跨租户平台财务总台或后台独立公共壳。

## 已实现行为

- 新建充值订单保存商品、渠道、金额与币种快照；打开零额账户以固定工作区币种，不宣称已收款。已有账户币种不符时拒绝下单。待支付详情提供经过 HTTPS/host 校验的付款入口、有效期、查询及关单。
- 统一网关使用固定端点、稳定命令键、请求/响应/回调签名。核对商户、供应商、对象、金额、币种和原交易号后才入账。HTTP 成功或本地超时、过期不被当成收款、退款或已关单的证据。
- 命令认领和回执持久化，同键并发复用同一订单及外部身份；事件 ID 不可变，支付/退款交易号不能跨单复用。未知状态可继续查询。已关闭订单仍可接收真实晚到支付，已支付订单不能被未付款状态回退。
- 退款引用原充值订单及可核验入账依据，申请时从 available 转入 held，生成任务不能使用该预留。申请人与批准人分离，批准要求当前财务审批权限；申请人可以拒绝自己的待审批申请以撤销，其他人拒绝须具备财务审批权限。
- 审批按原订单总额 `approvalBasisMinor` 判断 MFA，部分退款不能降低要求。缺少审批阈值时不允许批准，达到阈值但没有可信验证器时同样拒绝。当前生产组合未提供 MFA 验证器。
- 批准后真实通道状态可为 processing/unknown；只在核验 succeeded 后结算 held 并累计原单退款额。核验 failed 或拒绝才释放预留，原付款及已发生流水不可修改或删除。
- 未建立完整资金来源桶，退款资格保守绑定可核验账户版本、消费及业务冻结依据；后续未知账户写入使原充值未消费无法证明时拒绝自动退款，不用补偿入账替换已消费本金。未关联历史订单的 `creditMinor=null`，不推断为 0 或应付金额，不授予自动现金退款资格。
- API Key、项目级财务授权和伪造/不匹配工作区头不能扩权。检查工作区唯一可信租户、物理同库、当前权限、金额上限、版本和幂等指纹；完成回执重放仍重新授权。所有实际变更追加审计与 outbox，付款 URL 从审计中排除。
- 前端三语、筛选/分页与精确订单/退款深链；身份和工作区隔离草稿。第一次提交前持久保存独立幂等键，已尝试的表单冻结原输入，离开页面或响应丢失后仍重试原命令；明确放弃本地草稿不冒充取消服务端交易。
- 旧 HTTP 弱支付回调、旧后台直接标记现金退款或改订单状态已拒绝写入；内部显式传入 secret 的兼容 Python 调用不是生产公开回调。任务失败/客服余额补偿仍保留为独立账本流程，页面明确与现金退款区分。

## 接口与部署

新增 `/api/v1/workspaces/{workspaceId}/payments` 下商品目录、订单/退款列表、订单详情、创建和动作命令，以及独立签名入口 `/api/v1/payment-gateway/events`。新账单聚合读取为 `/api/v1/workspaces/{workspaceId}/billing/workspace`。

统一网关合同及启用条件见 [payment-gateway.md](../payment-gateway.md)，示例环境项见仓库 `.env.example`。这是项目自定义网关合同，尚未声称接通任何支付品牌的原生协议。七项网关/商品/渠道配置需完整有效；支付数据库与现有生成、音频、剪辑、财务和团队账本必须指向同一权威物理来源。服务不自动建缺表。

迁移 `b0e5e8effffa`（父版本 `a9d4d7deeee9`）创建五张支付表；PostgreSQL 保护事件、审计和资金流水不可变。降级拒绝删除已有支付证据，部署应采用向前修复。迁移未应用生产数据库。

## 浏览器与守恒核对

原型浏览器与实际页面在 1264px 宽度核对。应用预览使用真实认证入口、本地虚拟申请人/审批人、实际 Billing/PaymentRuntime 和隔离 SQLite；外部网关为注入的预览端口，checkout host 为不可真实付款的 `checkout.preview.invalid`。没有打开付款页，没有发生真实收退款。

实际操作并回读：

1. 新建 100 元充值单为 pending，账户不入账；通过关单命令变为 closed，无收款流水。
2. 对已核验的 100 元充值申请 20 元部分退款：available 从 867.25 变为 847.25，held 从 10.00 变为 30.00；申请人没有批准入口。
3. 通过登录页面切换第二名审批人，批准后为 processing，held 仍为 30.00，原单尚未计入退款。
4. 查询同一退款，网关端口给出明确 succeeded，held 降回 10.00，available 保持 847.25，原单累计退款为 20.00。处理记录保存申请人和审批人，成功后不再提供重复退款查询动作。
5. 账单按支付退款来源筛选为三条：该申请的 reserve/settle 与另一仍 processing 的 reserve；账户指标及七日结算趋势保持全工作区口径。后台退款页读取同一原单、金额与状态；历史补偿入口可达，未配置的旧后台服务明确不可用。

浏览器业务库 26 笔流水的 signed postings 重算为 available=84725 / held=1000 / spent=2275，与 canonical account（version 26）精确一致；各原单累计退款等于其 succeeded 退款之和，processing 退款只占用 held。最终来源的额外项目头、币种及审计守卫由上述直接 HTTP/SQL 验证覆盖，预览进程未重启覆盖这些增量，不将旧进程操作声称为全部最终源验收。
